# Multi-Mode Architecture Foundation

## Problem/Goal
Build the foundational architecture to support multiple game modes (Physics Puzzle, Rhythm Mode, Battle Royale, Level Editor) in the Web Pong game. Currently, the game only supports classic Pong gameplay. This task establishes the mode selection system, state management, and navigation infrastructure needed for future game modes.

## Success Criteria
- [ ] Mode selection system implemented
- [ ] State management supports multiple game modes
- [ ] Navigation between modes works seamlessly
- [ ] Architecture foundation allows easy addition of new modes

## Context Manifest

### How the Current System Works: Navigation and State Management

**Entry Point and Initialization:**

When the application starts, `main.jsx` renders the `App.tsx` component into the DOM root. There is no routing library (no React Router) - navigation is handled entirely through Zustand state management. The app uses a simple conditional rendering pattern based on the current mode stored in Zustand.

**Current Navigation Flow:**

The app starts with `currentMode: 'menu'` (default state in Zustand). The `App.tsx` component subscribes to this state using `const currentMode = useGameStore((state) => state.currentMode)`. Based on this value, it conditionally renders one of three things:

1. **Menu Mode (`currentMode === 'menu'`)**: Renders `<MainMenu />` component which displays a grid of game mode cards
2. **Classic Mode (`currentMode === 'classic'`)**: Renders the `<PongGame />` component with a header
3. **Other Modes (puzzle, rhythm, battle-royale, editor)**: Shows a "Coming Soon" placeholder with a button to return to menu

This pattern is implemented in `App.tsx` lines 18-34 using a simple if-else chain. The `SettingsPanel` component is rendered as an overlay regardless of mode and shows/hides based on its own `settingsPanelOpen` state.

**Zustand Store Architecture (`useGameStore.ts`):**

The global game store manages all cross-mode state. Here's what it currently contains:

- **`currentMode`** (GameMode): One of 'menu' | 'classic' | 'puzzle' | 'rhythm' | 'battle-royale' | 'editor'
- **`soundEnabled`** (boolean): Global sound toggle
- **`currentTheme`** (string): Theme ID for manual theme selection
- **`settingsPanelOpen`** (boolean): Controls settings panel visibility

The store provides these actions:
- **`setMode(mode: GameMode)`**: Changes the current game mode, which triggers App.tsx to re-render with the appropriate component
- **`toggleSound()`**: Flips sound state
- **`setTheme(themeId: string)`**: Manually sets theme (normally auto-switches by mode)
- **`toggleSettingsPanel()`**: Opens/closes settings overlay
- **`returnToMenu()`**: Sets mode back to 'menu' and closes settings

**Game Mode Metadata System:**

The `GAME_MODES` array (lines 49-85 in `useGameStore.ts`) defines metadata for all modes:

```typescript
{
  id: 'classic',           // GameMode identifier
  name: 'Classic Mode',    // Display name
  description: '...',      // Card description
  available: true,         // Whether mode is implemented
  icon: '🎮'              // Emoji icon for card
}
```

This array drives the MainMenu's mode selection grid. Only modes with `available: true` can be selected. Currently only 'classic' is available; the other four modes (puzzle, rhythm, battle-royale, editor) are marked as unavailable.

**MainMenu Component Architecture (`MainMenu.tsx`):**

The menu renders a full-screen experience with decorative elements (animated paddles, particle background, floating energy ball). The core is a grid of mode cards generated by mapping over `GAME_MODES`. When a user clicks an available mode card, it calls `handleModeSelect()` which invokes `setMode(modeId)` from Zustand. This state change triggers App.tsx to unmount MainMenu and render the selected game mode component.

The menu also includes a settings button that calls `toggleSettingsPanel()`, which opens the SettingsPanel overlay without changing modes.

**Theme System and Mode Integration:**

The app has a sophisticated theme system that automatically switches visual themes based on game mode. The `useTheme()` hook (in `useTheme.ts`) subscribes to both `currentMode` and `currentTheme` from Zustand. It implements this priority logic:

1. If user manually selected a theme in settings AND we're in menu mode, use that theme
2. Otherwise, use the mode-specific theme from `MODE_THEMES` mapping
3. Fall back to default 'synthwave-sunset' theme

The `MODE_THEMES` mapping (in `rendering/types.ts` lines 333-340) associates each game mode with its designated theme:
- menu → synthwave-sunset
- classic → synthwave-sunset
- puzzle → puzzle-logic (green/amber)
- rhythm → rhythm-beats (neon blue/cyan)
- battle-royale → battle-intensity (red/orange)
- editor → editor-pro (cool gray/blue)

When the theme changes, `useTheme()` calls `applyThemeAsCSSVariables(theme)` which sets CSS custom properties on the document root. This allows both Canvas rendering (via GameRenderer) and CSS styles to use the same theme colors.

**Current PongGame Component State Management:**

The PongGame component uses a **hybrid state approach** that's critical to understand for mode architecture:

- **Performance-critical game state**: Stored in `useRef` (not React state) for 60fps performance. This includes ball position, paddle positions, velocities, physics data, power-ups, etc. The entire game loop runs without triggering React re-renders.

- **UI-affecting state**: Uses React `useState` for things like `gameStarted`, `aiEnabled`, `aiDifficulty`, `showLeaderboard` - anything that needs to trigger UI updates.

- **Module instances**: Renderer, AudioManager, and other engine modules are stored in refs (`rendererRef`, `audioManagerRef`) and initialized once in a `useEffect`.

The game loop uses `requestAnimationFrame` for smooth 60fps updates. The animation frame ID is stored in a ref and properly cleaned up on unmount. This pattern is essential because switching modes will unmount/remount components.

**Settings Panel Overlay Pattern:**

The SettingsPanel is always rendered in App.tsx (line 37) but conditionally displays based on `settingsPanelOpen` state. When open, it shows a modal overlay with:
- Sound toggle (syncs with global `soundEnabled` state)
- Theme selector grid (all 6 themes available)
- About information

The panel uses event propagation stopping (`onClick={(e) => e.stopPropagation()}`) to prevent closing when clicking inside the panel, while the overlay background closes it on click. This pattern works across all modes because it's rendered at the App level.

### For Multi-Mode Architecture: What Needs to Connect

**Current Gaps in Architecture:**

The `src/modes/` directory exists but is empty. Game mode components currently live elsewhere:
- Classic mode: `src/components/PongGame.tsx` (1302 lines - monolithic)
- Other modes: Not yet implemented

The current architecture treats "Classic Mode" as the default game rather than one mode among many. To properly support multiple modes, we need:

**1. Component Migration Strategy:**

Currently, when `currentMode === 'classic'`, App.tsx renders `<PongGame />` directly. For a proper multi-mode architecture, each mode should be a self-contained component in `src/modes/`:

- `ClassicMode.tsx` - Extract/refactor from current PongGame.tsx
- `PhysicsPuzzleMode.tsx` - New component for puzzle mode
- `RhythmMode.tsx` - New component for rhythm mode
- `BattleRoyaleMode.tsx` - New component for battle royale
- `LevelEditorMode.tsx` - New component for level editor

Each mode component will:
- Manage its own game state using the same hybrid ref/state pattern
- Use shared engine modules (PhysicsEngine, GameRenderer, AudioManager, etc.)
- Render its own UI and controls specific to that mode
- Subscribe to global Zustand store for sound settings and theme
- Clean up properly on unmount (cancel animation frames, clear listeners)

**2. Routing/Navigation Pattern:**

Instead of the current if-else chain in App.tsx, we need a cleaner pattern. Options:

**Option A - Component Map (Current pattern, improved):**
```typescript
const MODE_COMPONENTS = {
  'menu': MainMenu,
  'classic': ClassicMode,
  'puzzle': PhysicsPuzzleMode,
  'rhythm': RhythmMode,
  'battle-royale': BattleRoyaleMode,
  'editor': LevelEditorMode,
};

const ModeComponent = MODE_COMPONENTS[currentMode] || MainMenu;
return <ModeComponent />;
```

**Option B - React Router (adds dependency):**
Use react-router-dom with routes like `/menu`, `/classic`, `/puzzle`. This adds URL-based navigation but requires installing a new dependency and handling deployment paths (currently uses base: '/w3bP0ng/').

Recommendation: **Option A** - Stick with the stateful navigation pattern. It's simpler, no new dependencies, and mode switching is instant without URL updates. This matches the game-like feel better than traditional web routing.

**3. Shared State Architecture:**

Different modes need different game state structures:
- Classic: 2 paddles, 1 ball (potentially multi-ball)
- Battle Royale: 8 paddles, multiple balls, elimination tracking
- Puzzle: 1 paddle, obstacles, level data, win conditions
- Rhythm: Beat tracking, combo system, score multipliers

But they all share:
- Sound settings (from Zustand)
- Theme/visual settings (from Zustand)
- Leaderboard data (localStorage, per-mode)
- User preferences (localStorage)

The current Zustand store handles shared settings well. Each mode component will manage its own game-specific state in refs (for performance) while subscribing to the shared Zustand state for settings.

**4. Engine Module Reusability:**

The extracted modules are already well-designed for reuse:

- **PhysicsEngine** (`src/engine/PhysicsEngine.ts`): Pure functions for ball movement, paddle updates, momentum calculations. All modes can use these or extend them.

- **CollisionDetector** (`src/engine/CollisionDetector.ts`): Geometric collision detection. Works for any ball-paddle collision. Puzzle mode will need additional obstacle collision functions.

- **GameRenderer** (`src/rendering/GameRenderer.ts`): Canvas 2D renderer with theme support. Takes a `RenderState` interface and draws it. Each mode will need to construct its own RenderState shape, but the renderer can be extended with mode-specific drawing methods.

- **AudioManager** (`src/audio/AudioManager.ts`): Web Audio API sound effects. Works across all modes. Will need Tone.js integration for Rhythm Mode's music system.

- **AIController** (`src/ai/AIController.ts`): Currently 2-player specific. Battle Royale will need multi-AI coordination. Puzzle mode doesn't need AI.

- **PowerUpManager** (`src/powerups/PowerUpManager.ts`): Modular power-up system. Classic and Battle Royale can use directly. Puzzle mode might repurpose for level objects.

**5. Theme and Visual Differentiation:**

Each mode already has a designated theme in `MODE_THEMES`. When a mode component mounts, the `useTheme()` hook will automatically switch to that mode's theme. The `GameRenderer.setTheme(theme)` method updates the canvas renderer, and `applyThemeAsCSSVariables(theme)` updates CSS variables for UI components.

This means each mode component should:
- Call `useTheme()` to get current theme
- Pass theme to GameRenderer instance via `setTheme()`
- Trust that CSS variables are automatically updated for UI

The MainMenu already uses theme CSS variables for its decorative elements (via `--theme-ball`, `--theme-paddle-left`, etc.).

**6. Transition/Animation System:**

Currently, mode switches are instant (unmount old component, mount new one). For polish, we'll want:
- Fade out current mode
- Optional loading state
- Fade in new mode

This can be implemented with:
- GSAP (already installed) for smooth animations
- Zustand state for transition status (optional)
- CSS transitions on App container

The MainMenu already has sophisticated animations (particle background, floating ball, paddle animations). These serve as patterns for mode transition animations.

**7. Data Persistence Strategy:**

Current persistence:
- Leaderboard: `localStorage.getItem('pong-leaderboard')` - stored in PongGame component
- No user preferences persistence yet
- No progress/save data yet

For multi-mode:
- Each mode should have its own leaderboard key: `'leaderboard-classic'`, `'leaderboard-rhythm'`, etc.
- Puzzle mode will need level progress: `'puzzle-progress'` (which levels completed, star ratings)
- Editor mode will need saved levels: `'editor-levels'` (array of level JSON)
- Global settings (sound, theme) could be persisted but currently aren't

Recommendation: Create a `src/utils/storage.ts` module with typed localStorage helpers:
```typescript
export function saveLeaderboard(mode: GameMode, scores: Score[]): void
export function loadLeaderboard(mode: GameMode): Score[]
export function savePuzzleProgress(progress: PuzzleProgress): void
```

#### Important Implementation Notes

1. **No React Router**: Stay with stateful navigation via Zustand. Simpler, faster, no URL complexity.

2. **Mode Component Location**: All mode components must go in `src/modes/` to match the path alias `@modes/` and follow the architecture defined in PROJECT_ROADMAP.md.

3. **Shared vs Mode-Specific State**:
   - Shared (Zustand): currentMode, soundEnabled, currentTheme, settingsPanelOpen
   - Mode-specific (refs): game state, physics data, score, timers, entity positions
   - UI-specific (useState): paused, showing menus, button states

4. **Theme Auto-Switching**: When a mode mounts and calls `useTheme()`, it automatically gets its designated theme. No manual theme switching needed unless user overrides in settings.

5. **Cleanup is Critical**: Each mode MUST clean up animation frames, event listeners, and timers on unmount. Otherwise, switching modes will cause memory leaks and performance issues.

6. **Engine Module Patterns**:
   - PhysicsEngine: Pure functions, call with current state, get new state
   - GameRenderer: Stateful class, create once, call `render(state)` each frame
   - AudioManager: Stateful class, create once, call `playSound()` methods
   - All tested with 100% coverage, safe to reuse

7. **Performance Budget**: Current bundle target is <512KB. Adding 4 new mode components will increase bundle size. Use code splitting via Vite's `manualChunks` if needed (already configured for vendor chunks).

8. **Accessibility**: All modes must support keyboard navigation and screen reader labels, following patterns from PongGame (lines 1046-1061) and SettingsPanel (lines 24-26, aria attributes).
